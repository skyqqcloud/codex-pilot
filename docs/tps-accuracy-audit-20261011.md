# TPS 统计审计 · 2026-10-11

本次检查针对 Codex Pilot 2.6.0，并修正为 2.6.1 / build 27。这里的 TPS 定义为客户端观测的非推理输出阶段速率，不能作为服务端模型内部持续生成速度的精确测量。

## 口径和边界

- 分子：API 完成用量中的 `outputTokens − reasoningTokens`。推理属于新输出，但当前分段指标不计入推理；输入及缓存不计入。这个差值仍含工具参数和未单列的格式 token，不精确等同于可见正文。
- 分母：本地 Codex 日志中第一个明确的 message/function_call/custom_tool_call 输出项到官方完成事件的客户端时间。不是服务端 GPU 计时，也不把两次调用之间的闲置或本地工具执行摊进去。
- 后续推理、网络缓冲和客户端处理延迟可能落入该区间，无法完整拆分。短输出集中到达时，比值可能很高，不能据此认定模型具有同样的持续生成速度。
- 缺少可靠起点的含推理记录保留用量，速率为「—」。已有日志显示更早输出项完成、或包含未知输出类型时，不拿后面一项当作完整起点。零推理记录可以使用原采集的首输出到完成区间。
- 最近五次平均：先按模型取最近五条已采集完成记录，再对其中可测的逐次速率做等权算术平均。缺计时不当作零，不用第六条补位。采集关闭、失败、缺完整用量等未形成记录的调用不在该窗口内；不能声称覆盖全部真实 API 调用。

参考：[OpenAI reasoning 说明](https://developers.openai.com/api/docs/guides/reasoning)、[OpenAI 输出 token 计数说明](https://developers.openai.com/api/docs/guides/token-counting)。

## 复现并修正的采集问题

1. 完成事件缺少推理字段时，旧实现默认成 0。现在要求输入、输出、推理、缓存四项合法整数明确存在；缺失、负值、小数和子集越界均拒绝，既不夹取也不截断。
2. 两条重叠流中的一条失败，会清空旧配对状态，导致剩余流的结束事件可能与新起点误配。已复现错误样本 `start=4, end=6, output=999`；修正后保留不可配对状态，直到这些流结束，不生成该样本。
3. 未结束状态过期后，旧起点分支提前返回，使下一个正常调用被阻塞。现在先清理过期状态，再处理新起点。
4. 重发旧导出批次、迟到的开始或完成事件可能影响新配对。现在维护有界事件去重和已结束时间，旧批次不重开旧请求；无起点的结束事件也会阻止后续迟到起点形成幽灵请求。
5. 分段耗时超过本次 API 总时长、开始时间非有限、输入缓存矛盾等记录，不进入速率计算。一个坏边界不会使其他正常请求的日志关联全部失败。

配对仍依赖 conversation/model/time；官方日志未提供可用的完整请求 ID 链。重叠或边界不确定时拒绝测速，不猜测归属。这不构成对所有未来版本和未知传输行为的无误保证。

# 常驻能耗复查 · 2026-10-18

目标版本：Codex Pilot 2.8.2 / build 38。

## 查明的重复工作

2.8.1 的 QoS 分类生效，但每次刷新仍创建新的 Python 读取进程，从头扫描有关会话的 JSONL。相同输入再次关联也会重读；尚未找到输出的有限重试放大了成本。SQLite 使用已有 thread_id/时间索引，不需要修改 Codex 数据库。

修正 CPU 计数单位后，升级前 50.05 秒实际窗口内，主进程约 0.524 秒 CPU、采集器约 0.134 秒、临时读取器合计约 4.944 秒。此时有正常 Codex 调用，不是空闲测试。原 10 月 16 日报告的 CPU 毫秒换算错误，已在原文更正。

## 修改与边界

- 复用按 QoS 分类的读取进程：后台 background、自动 utility、交互 user initiated；只保留当前 Codex home，至多三个按需启动的读取器。空闲等待 stdin，没有轮询；管道关闭后退出。错误/异常退出后下次读取重建；单次读取超过 30 秒终止该读取器，保留原子发布的最后正常面板。
- 读取器按文件身份和偏移增量解析 append-only rollout。相同文件未变化时不重读；追加时只读后缀和小段边界校验；替换、截短、同尺寸改写或边界不符时失效重建。扫描中替换/截短拒绝发布。
- 每个读取器的内存 LRU 至多保留 96 个文件、24,000 条关联事实；不落盘。只存短摘要、身份、哈希和原文位置，不保留图片、推理、工具返回或完整历史。完整消息/输出/工具参数按所选调用从原文定位读取，并校验文件身份和记录哈希。
- 不缓存数值计时结果。每次需要重新校验时仍读取最新的显式类型输出事件，带齐受影响会话的相邻调用并拒绝重叠或不足证据。TPS 分子、分母、最近五次平均、原始采集和保留规则未修改。

## 核对

- 本机同一快照 520 条样本：新旧 323 个上下文完全一致；六个模型选中调用的完整用户/输出/工具内容完全一致。244 条可解析计时完全一致。计时函数源码和 Swift TPS 公式源码逐字一致。
- 最大会话的三个文件共 348,536,001 字节；旧版一次关联 CPU 约 0.317 秒，新版冷建索引约 0.419 秒，热关联约 0.0089 秒、读取 rollout 0 字节。首次建索引仍需扫描，不能把热关联结果说成冷启动性能。
- 16 项账号、30 项采集、33 项上下文和 13 项 Swift 统计检查通过。新增测试覆盖增量读取量、未写完的 UTF-8 行、乱序查询窗口、追加重叠调用、文件替换/截短/改写、陈旧原文引用、LRU、归档发现及管道 EOF。
- 原生检查通过读取器 PID 复用、异常退出恢复、三类真实子进程 QoS、失败保留正常分组、固定列表高度、折叠/选中、浅深色及 80 次稳定重绘。
- 已安装并启动 2.8.2/build 38，二进制和三个后端资源与构建产物一致，签名验证通过。七个受保护的配置/登录文件保持一致；启动后核对共同保留的 513 条样本，用量、计时、模型、档位及会话身份均未变，正常采集新增七条。启动补齐六条消息摘要，属于既有采集器的关联行为。
- 新版 50.38 秒现场窗口：主进程 0.083 秒 CPU、两个读取器合计 0.276 秒、采集器 0.950 秒。三个子进程在窗口首尾均存在，没有重复创建读取进程，两个读取器与采集器的中断唤醒均为零。合计 1.309 秒 CPU，约一个核心的 2.60%；此前窗口的读取器为 4.944 秒。两轮真实调用量和数据不同，不能直接推算长期节电百分比。
- 内存复查：受控回放的索引对象约 9.3 MiB（约 12,400 条事实），不是完整日志缓存；实际进程占用还包含 Python、库和分配器保留页。现场 vmmap 看到较大的空闲 malloc 区，不能把索引对象大小说成整个读取器的内存。本轮没有增加周期垃圾回收或内存清理定时器。

## 测量限制

CPU 受控回放使用 Python `time.process_time()`。进程现场计数使用 `proc_pid_rusage` 并按 Mach timebase 换算；已用一秒 CPU 工作负载核对单位。未完成升级后的 12 小时能耗窗口，不承诺长期耗电降低比例，也不保证固定使用能效核。

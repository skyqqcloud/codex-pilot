# 常驻能耗检查 · 2026-10-16

适用版本：Codex Pilot 2.8.0 / build 36。此轮保持 TPS 定义、原始用量、每模型 100 条保留策略和对话分组规则。

## 修改

- 取消无界面用途的旧分钟统计扫描及 15 秒轮询，监听样本目录变化；没有新文件内容时不启动上下文读取进程，连续事件合并到最多每 15 秒一次。
- 仅重新准备发生变化的会话，数值和分组原子发布；最近尚未完整写入的关联最多重试 3 次。受影响会话的相邻请求重新校验计时，避免缓存掩盖新增的重叠边界。
- 遥测接收器仅在新增有效完成记录时写样本，诊断文件最多每分钟写一次；使用 kqueue 等待请求或父进程退出，取消每秒检查。
- 上下文读取只保留关联所需事实，跳过推理和无关记录，在解析前剔除 image_url 内的图片数据；完整详情仍在选中时读取。
- 所选请求详情按自己的上下文变化刷新，其他请求更新不触发重复读取；关闭全部额度自动刷新后不保留额度定时器。

## 尚未验证

新版没有完成新的 12 小时能耗观察窗口，不能据此声称已经达到某个长期节电比例。活动监视器的「12 小时电源」是相对能耗影响指标，不是瓦时或电池百分比；升级后旧版本的历史仍会影响该值。

## 2.8.1：QoS 调度分类

- 常驻采集器、文件监听及自动历史整理使用 background；自动额度刷新使用 utility；手动详情、额度刷新、设置及账号操作使用 user initiated。
- 日志和账号子进程在启动前显式设置 `Process.qualityOfService`，依据 Swift 任务的有效优先级映射。用户等待共享任务时允许 Swift 的自动优先级提升，保持前台响应。
- 不绑定 CPU 核心，不改系统调度策略。QoS 表达工作的紧迫程度，实际使用能效核或性能核由 macOS 决定。
- 原生检查通过真实 Python 子进程验证：background 为 QoS 9，utility 为 17；用户任务为 25 或更高；实际 `TelemetryCapture.start()` 启动的采集器为 background。
- 真实接收器以 background QoS 运行，4 个并发发送方提交 40 批、160 次模拟 API 调用，全部保留且无重复，输入、输出、推理、缓存、耗时与等待均符合给定数据。只使用隔离本机服务，没有调用真实模型。
- 84 项功能与统计检查、QoS 子进程检查及原生布局检查通过。首轮原生检查因测试包未预置新探针脚本失败，补齐测试资源后通过。
- 三个 Python 后端和 TPS 公式源码与 2.8.0 一致。本轮未测量 P/E 核占用分布，也未完成新的长期电池耗电对照。
